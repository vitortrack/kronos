# Latency, turn and token efficiency in coding-agent harnesses, and long-session persistence/resume

Context for the reader: TrackAI runs mostly on glm-5.3-flash (Ollama cloud). The model takes 92-97% of wall time, each step costs at least ~1-2 s, and a typical task is ~20-27 main-agent steps plus 5-10 reviewer steps (the reviewer is 25-35% of time). Thinking is already adaptive. A prompt asking the model to batch edits had no measurable effect. Read-only tools already run in parallel. There is no session resume. Research date: 2026-11-09. Every number below is dated and gives its setup. Items marked "abstract-level" were read only from the abstract or search snippet, not the full paper.

## 1. Parallel tool calls, batching and speculation: measured reductions in turns/latency, and whether models follow batching instructions

### Takeaway
The large, well-measured wins come from structural changes, not from prompting. Examples are a planner that emits a whole DAG of calls (LLMCompiler, up to 3.7x faster), code-as-action, where one script makes many tool calls (CodeAct, up to 30% fewer actions; Anthropic Programmatic Tool Calling, "19+ inference passes" removed for 20+ calls), and speculative execution of the likely next action (about 20% lossless time saved, with a theoretical ceiling of 50%). Prompting for parallelism works on models trained for it, but Anthropic says how the message history is formatted "teaches" the model whether to parallelize. No source measures whether open models such as GLM follow batching instructions.

### Cited Findings
**Parallel/DAG function calling**
- LLMCompiler (Kim et al., ICML 2024; arXiv v1 Dec 7 2023, v3 Jun 5 2024): a planner emits a dependency graph of function calls and an executor runs independent calls in parallel. Compared with ReAct it reports **up to 3.7x latency speedup, up to 6.7x cost savings and up to ~9% accuracy improvement**. It works with open and closed models. The abstract does not name the benchmarks — [arXiv 2312.04511](https://arxiv.org/abs/2312.04511)
- CodeAct (Wang et al., UIUC/Apple, ICML 2024; arXiv 2402.01030): actions are executable Python, so one action can chain or loop over several tools. Across 17 LLMs on API-Bank and the authors' M3ToolEval it reports **up to 20 percentage points higher success while requiring up to 30% fewer actions**, with larger gains on complex tasks. A secondary review claims "2.1 fewer turns on average" for GPT-4-1106, but this was not confirmed in the paper — [arXiv 2402.01030v4](https://arxiv.org/html/2402.01030v4)
- Anthropic "Advanced tool use" (Nov 24 2025), Programmatic Tool Calling (PTC): Claude writes one script that calls many tools, and only the final output returns to context. "Orchestrating 20+ tool calls in one code block eliminates 19+ inference passes." On complex research tasks, average tokens fell **43,588 → 27,297 (-37%)**. Internal knowledge-retrieval accuracy went **25.6% → 28.5%** and GIA **46.5% → 51.2%**. A 200 KB expense dataset was reduced to 1 KB in context — [Anthropic Engineering](https://www.anthropic.com/engineering/advanced-tool-use)
- Same post, other context savers: Tool Search cut upfront tool-definition context from **~77K to ~8.7K tokens (-85%)** for 50+ MCP tools. MCP-eval accuracy rose **Opus 4: 49% → 74%; Opus 4.5: 79.5% → 88.1%**. Tool-use examples raised complex-parameter accuracy from **72% to 90%** (internal testing) — [Anthropic Engineering](https://www.anthropic.com/engineering/advanced-tool-use)

**Do models follow batching instructions? (vendor guidance, no numbers)**
- Anthropic docs (fetched 2026-11-09): "Claude 4 and later models make parallel tool calls by default when a request benefits from multiple tools." The recommended system prompt is: "For maximum efficiency, whenever you need to perform multiple independent operations, invoke all relevant tools simultaneously rather than sequentially." A stronger `<use_parallel_tool_calls>` variant adds examples such as "when reading 3 files, run 3 tool calls in parallel" — [Claude docs: Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- Same page, troubleshooting: "The most common issue is formatting tool results incorrectly in the conversation history. This 'teaches' Claude to avoid parallel calls." Wrong: one user message per tool_result. Correct: all tool_results in one user message, before any text. To avoid dependent calls being batched, the page suggests adding "Only batch tool calls that are independent of each other." If a call fails because its prerequisite had not finished, return `is_error: true` and the model reissues it next turn — [Claude docs: Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- Same page: a note says one recent model "may issue fewer parallel tool calls than earlier models, most noticeably in long agent loops where the next reads are only implied (custom coding agents, bash and text editor harnesses)", and that it needs an explicit batching instruction. So parallel-call propensity varies by model and checkpoint even within one vendor — [Claude docs: Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- GLM on Ollama: no source was found that confirms GLM-4.6/GLM-5 emit several tool calls per response through Ollama. Z.ai sample code collects tool calls by index, which suggests multi-call is possible but does not state it. A community Ollama upload says Ollama's template re-maps GLM tool calls into a Qwen3-like JSON schema (unofficial) — [Z.ai GLM-4.6 migration](https://docs.z.ai/guides/overview/migrate-to-glm-4.6); [Ollama community GLM-4.6](https://ollama.com/MichelRosselli/GLM-4.6)

**Speculative actions / speculative tool execution (2025-2026)**
- Speculative Actions (Ye, Ahuja, Liargkovas, Lu, Kaffes, Peng; Columbia; arXiv Oct 5 2025; ICLR 2026 poster). A fast Speculator guesses the next action and pre-executes up to k guesses. The result is committed only if the authoritative Actor picks the same action, so it is lossless. Chess (GPT-5 low vs high effort): **~54.7% next-action accuracy with 3 guesses, 19.5% average time saved**. τ-bench retail: **22-38%** of API calls predicted. HotpotQA ReAct: **up to 46% top-3** accuracy. The theory bounds the runtime reduction at **≤50%** even with perfect prediction. Token cost goes up with k; exact numbers are given only for the OS-tuning case (1.18 vs 0.35 cents at 60 s) — [arXiv 2510.04371](https://arxiv.org/html/2510.04371v1)
- Related, abstract-level only: SPAgent (search agents) **up to 1.65x** end-to-end speedup at the same or better accuracy — [arXiv 2511.20048](https://arxiv.org/html/2511.20048v1). DualSpec (deep-research agents, Mar 2026) **up to 3.28x** end-to-end speedup, comparable to the full-reasoning model — [arXiv 2603.07416](https://arxiv.org/pdf/2603.07416). "Speculative Tool Calls" (Dec 2025) covers engine-side optimizations that keep sequences resident in the inference engine — [arXiv 2512.15834](https://arxiv.org/abs/2512.15834v1). PASTE (pattern-aware speculative tool execution, 2026) — [arXiv 2603.18897](https://papers.mewayz.com/paper/arxiv_2603.18897)

### Inferences
- TrackAI's failed "batch your edits" prompt matches the vendor guidance. Batching depends on model training and on the history the model sees. Three checks come first: (a) measure the fraction of responses with ≥2 tool_calls from glm-5.3-flash, (b) confirm that all tool results for one assistant turn go back in a single message, and (c) confirm that Ollama's GLM template keeps multiple calls. If (a) is near 0, prompting cannot help.
- With 92-97% of time in the model and ≥1-2 s per step, the lever is fewer model steps. Changing the action space is the proven way to get them, rather than asking for it. Options include a multi-edit or apply-patch tool that takes N hunks across files, a multi-file read tool, and a "run a short script that calls tools" action (CodeAct/PTC style). These turn N steps into 1 by construction.
- Deterministic harness-side prefetch is cheap speculation with no extra model calls. Examples are auto-reading the top grep hits, auto-running typecheck or tests after an edit, and attaching the result to the same tool_result. Each one removes a predictable "now run X" step. Model-based speculation (Speculative Actions) costs extra tokens and gives about 20% at best in published setups.

### Gaps
- No published measurement of parallel-call rate or batching-instruction compliance for GLM-4.x/5.x (or for most open models) in coding loops.
- No source gives a measured number for "turns saved by parallel tool calls" in a coding agent such as Claude Code or Codex. Vendor docs give guidance only.
- OpenAI's `parallel_tool_calls` documentation was not fetched in this session.

## 2. Token/turn efficiency: cost vs success, early stopping and step limits, routing to cheaper models, prompt caching

### Takeaway
Agent cost is dominated by re-sent input tokens (~99% input in one Claude 4 Sonnet measurement; ~100:1 input:output at Manus). Accuracy-only agent designs can cost 50x more for equal or worse accuracy. Measured savings at the same accuracy come from trajectory pruning or observation masking (-21% to -50% cost), prefix caching (up to -90% cost and -79% TTFT on long prompts), and cheap-then-escalate routing (vendor claims of -39% to -46%, not independently verified). Over-long reasoning hurts agentic success.

### Cited Findings
**Cost vs accuracy**
- "AI Agents That Matter" (Kapoor et al., arXiv Jul 1 2024): HumanEval, 164 problems, mean of 5 runs, Apr 2024 GPT-4-Turbo/GPT-3.5 pricing. Simple baselines **Warming 93.2% at $2.45 and Retry 92.0% at $2.51** vs **LATS(GPT-4) 88.0% at $134.50** (~55x the cost for lower accuracy) and **Reflexion 87.8% at $3.90**. Escalation (cheap model first, escalate on failure) reached **85.0% at $0.27**. "For substantially similar accuracy, costs can differ by almost two orders of magnitude." The paper also notes SWE-agent capped tasks at $4/task, so one SWE-bench run could exceed $8,000 — [arXiv 2407.01502v1](https://arxiv.org/html/2407.01502v1)
- Same paper, joint cost/accuracy optimization (DSPy on HotPotQA, May 2024 pricing): **-53% variable cost (GPT-3.5)** and **-41% (Llama-3-70B)** at similar accuracy — [arXiv 2407.01502v1](https://arxiv.org/html/2407.01502v1)
- A 2026 paper cited secondhand says agentic runs on the same SWE-bench Verified task can vary by **up to 30x in total tokens** and that models predict their own cost poorly (not read directly) — [secondary blog on routing](https://getunblocked.com/blog/model-routing-coding-agents)

**Context/trajectory reduction (input tokens are the bill)**
- AgentDiet (arXiv 2509.23586; FSE 2026). It prunes "useless, redundant, expired" content from the trajectory with an LLM reflection module. On SWE-bench Verified and Multi-SWE-bench Flash with 2 LLMs it reports **-39.9% to -59.7% input tokens and -21.1% to -35.9% total cost at the same resolve rate**. Motivation: **99% of tokens are input and 1% generated** (Claude 4 Sonnet usage on OpenRouter) — [arXiv 2509.23586](https://arxiv.org/html/2509.23586v1); [FSE 2026 listing](https://conf.researchr.org/details/fse-2026/fse-2026-research-papers/137/Reducing-Cost-of-LLM-Agents-with-Trajectory-Reduction)
- "The Complexity Trap" (arXiv 2508.21433, 2025), SWE-agent on SWE-bench Verified. Simple **observation masking (hide old tool outputs) roughly halves cost vs the raw agent** and matches or slightly beats LLM summarization in solve rate. A hybrid on Verified-50 with Qwen3-Coder-480B was **-7% cost vs masking and -11% vs pure summary, +2.6 pp solve rate vs raw** (third-party overview) — [arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- OpenHands context condenser (blog Apr 9 2025): **up to 2x lower per-turn API cost** with equal or better performance on a subset of SWE-bench Verified, plus steadier response times in long sessions. Vendor-reported — [OpenHands blog](https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents); [OpenHands SDK docs](https://docs.openhands.dev/sdk/guides/context-condenser)

**Overthinking / reasoning budget**
- "The Danger of Overthinking" (Cuadron et al., arXiv Feb 12 2025; 4,018 SWE-bench Verified trajectories). Higher overthinking scores correlate with lower resolve rates, and reasoning models overthink more. Two low-effort samples plus picking the less-overthinking one reached **27.3% for $800** vs high-effort o1 **29.1% for $1,400 (-43% cost)**. The abstract also claims "~30% better performance". Summaries disagree on that figure — [HF papers 2502.08235](https://huggingface.co/papers/2502.08235)

**Routing: cheap model for some steps, strong model for others**
- SWE-Router (arXiv 2607.00053, Jun 30 2026; ICML 2026). The cheap model runs "a few exploratory turns", then a learned value head decides whether to continue cheaply or escalate. The abstract claims it "greatly improves cost efficiency" while keeping "the majority" of strong-model performance. No numbers in the abstract — [arXiv 2607.00053](https://arxiv.org/abs/2607.00053)
- Vendor or small-sample claims (unverified). LiteLLM subtask-type router: **~46% lower cost** at equal results on a **9-task** SWE-bench Verified subset — [LiteLLM blog](https://docs.litellm.ai/blog/subtask-type-routing). Not Diamond: **~39% savings** at near-frontier quality on Poly-SWE-bench, **~66%** when mixing open and closed models — [Not Diamond](https://www.notdiamond.ai/blog/not-diamond-code-intelligent-model-routing-for-coding-agents). Practitioner warning: mis-routes that need rework can erase the savings — [Unblocked blog](https://getunblocked.com/blog/model-routing-coding-agents)
- Escalation baseline (Jul 2024): GPT-3.5 first, then GPT-4 on failure. **85.0% at $0.27** vs GPT-4 alone **89.6% at $1.93** on HumanEval — [arXiv 2407.01502v1](https://arxiv.org/html/2407.01502v1)

**Prompt / prefix caching**
- Anthropic prompt caching launch (Aug 2024). For long prompts, "up to 90%" lower cost and "up to 85%" lower latency. Measured cases: a 100K-token cached book prompt went from **TTFT 11.5 s → 2.4 s (-79%), -90% cost**; a 10K many-shot prompt had **-31% latency, -86% cost**; a 10-turn chat with a long system prompt had **-75% latency, -53% cost**. Cache writes are +25% and reads are -90% vs base input. Cache hits require an exact prefix match — [Anthropic news](https://www.anthropic.com/news/prompt-caching); [SD Times summary](https://sdtimes.com/ai/anthropic-introduces-prompt-caching-to-reduce-latency-and-costs)
- Manus "Context engineering" (Jul 18 2025). KV-cache hit rate is "the single most important metric" for production agents. Input:output ratio is **~100:1**, and a typical task makes **~50 tool calls**. Cached vs uncached Claude Sonnet input is **$0.30 vs $3/MTok (10x)**. Practices: stable prefix (no timestamps), append-only context, deterministic JSON key order, mask tools rather than removing them mid-task, session-ID routing for self-hosted vLLM prefix caching — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Anthropic docs (fetched 2026-11-09): changing `tool_choice` invalidates cached message blocks. Tool definitions and the system prompt stay cached — [Claude docs: Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)

### Inferences
- For TrackAI, the per-step floor (~1-2 s) is largely prefill plus round-trip. Two things shrink it: keeping the prompt prefix byte-stable and append-only, so Ollama or the provider can reuse KV cache, and masking or pruning stale tool outputs (observation masking is the cheapest proven option, at about -50% cost in SWE-agent). Neither reduces the step count. They reduce the cost of each step.
- Routing evidence for coding agents is still mostly vendor or small-sample. The one peer-reviewed design (SWE-Router) uses cheap model first, then a learned escalation decision. A cheap model for exploration plus the strong model for edits and decisions is plausible, but only an internal A/B on TrackAI tasks can establish the accuracy trade-off.
- Retry, warming and escalation baselines beat elaborate agent loops on cost in 2024. The same logic supports capping steps and doing a cheap retry over long single trajectories. The Overthinking result (Feb 2025) points the same way.

### Gaps
- No peer-reviewed number for step-limit effects (resolve rate vs max-steps curve) on SWE-bench was retrieved this session.
- Whether Ollama cloud does prefix/KV caching for glm-5.3-flash, and with what TTFT effect, is undocumented in the sources found. It needs internal measurement.
- GPT-5.1-Codex-Max announcement (Nov 2025, compaction and token-efficiency figures): the page returned HTTP 403, so no numbers from it are included.
- Anthropic's multi-agent research-system post (token-usage multipliers for multi-agent setups) was not fetched in this session.

## 3. Reviewer/verification cost reduction: cheaper verifiers, conditional review, skipping review for small diffs

### Takeaway
Always-on verification is expensive: up to 53.2x cost overhead measured on coding benchmarks. The 2025-2026 literature converges on adaptive policies: fast or cheap checks first, escalate only on risk or disagreement, and pick the verifier per step. These policies report lower cost at matched reliability. No study was found that measures "skip LLM review for small diffs" or code-review agents specifically, so the accuracy trade-off for TrackAI's reviewer is unmeasured.

### Cited Findings
- Sherlock (arXiv 2511.00330, Nov 2025): each verification adds LLM calls. Measured overhead is **up to 28.9x (instruction-following) and 53.2x (coding benchmarks)** in latency and cost. Verifier effectiveness and cost vary by task and node type, and expensive verifiers are not always the most cost-effective, so verifiers are selected per node — [arXiv 2511.00330](https://arxiv.org/html/2511.00330v1)
- FlexiVe (arXiv 2505.11966, 2025, math reasoning): a fast low-token verification mode is cheaper but less accurate on hard problems. Fast checks first, escalating when needed, manages the trade-off — [Emergent Mind 2505.11966](https://www.emergentmind.com/papers/2505.11966)
- Co-Sight (arXiv 2510.21557, 2025): agent systems "over-audit low-impact steps while missing subtle conflicts". It focuses verification on points of disagreement — [arXiv 2510.21557](https://arxiv.org/html/2510.21557v1)
- Anytime Verified Agents (TMLR 2026): adaptive compute allocation reduces cost at matched reliability thresholds vs always-verify, with comparable accuracy (no figures retrieved) — [mlanthology](https://mlanthology.org/tmlr/2026/patel2026tmlr-anytime/)
- Calibrate-Then-Act (arXiv 2602.16699, 2026): always-verify wastes cost and never-verify loses accuracy. It conditions the agent on priors to decide when verification pays off — [Emergent Mind 2602.16699](https://api.emergentmind.com/papers/2602.16699)
- Anthropic long-running harness (Nov 26 2025): Claude "often marked features complete after only unit tests or curl checks". Giving it browser-automation testing "dramatically improved performance" (qualitative, no numbers). This is an example of a verification signal that comes from a tool rather than from LLM judgment — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

### Inferences
- The reviewer takes 25-35% of TrackAI's time over 5-10 steps. Three measures fit the evidence. (a) Run deterministic checks first (typecheck, tests, lint), and invoke the LLM reviewer only when they pass and the diff crosses a risk threshold (size, touched paths, new files). (b) Hand the reviewer the diff plus check outputs in one prompt with a small step cap, so it does not explore with tools (fewer steps). (c) Use a cheaper or faster model for the reviewer, escalating on disagreement. All three are consistent with the adaptive-verification results. Their accuracy cost must be measured internally, for example by replaying past tasks with and without review and counting defects the reviewer caught.

### Gaps
- No found study quantifies defect-catch rate vs cost for LLM code reviewers in coding agents, or the effect of skipping review on small diffs.
- Full-text numbers for FlexiVe, Anytime Verified Agents and Derailer-Rerailer were not retrieved.

## 4. Long-running sessions: persistence, checkpoint/resume, measured effects

### Takeaway
Production harnesses (Claude Code, Codex CLI) persist sessions as append-only JSONL event logs and resume by replaying the log into a new context. Long logs need compaction or pagination. File-edit snapshots are kept separately from git. Anthropic's long-running pattern adds external state the agent re-reads each session: a progress file, a JSON feature list, git commits and init.sh. LangGraph checkpoints at step boundaries and stores per-node pending writes so completed work is not redone. None of these sources publishes a controlled measurement of resume or progress-file effects.

### Cited Findings
**Anthropic, "Effective harnesses for long-running agents" (Justin Young, Nov 26 2025)**
- Problem: each session starts without memory, and "compaction alone" was not enough. Even Opus 4.5 on the Agent SDK tried to one-shot the app and ran out of context mid-feature, or later saw progress and declared the job done — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Design: an **initializer agent** (first session) writes `init.sh`, `claude-progress.txt`, a feature list and an initial git commit. A **coding agent** (every later session) works on one feature, commits with descriptive messages and updates the progress file. The two differ only in their initial prompt; tools and harness are identical — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- The feature list had **200+ features** for a claude.ai clone, all initially "failing", each with steps and a `passes` field. Agents may only flip `passes`. JSON was chosen because the model is less likely to wrongly edit or overwrite JSON than Markdown — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Each session starts by running `init.sh` and a basic end-to-end check. This catches bugs left by the previous session and "saves tokens" because the agent need not work out how to run the app. No quantitative results or controlled comparison are reported — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Claude Code (docs fetched 2026-11-09)**
- "Each message, tool use, and result is written to a plaintext JSONL file under `~/.claude/projects/`, which enables rewinding, resuming, and forking." Before code changes, Claude Code snapshots the affected files — [Claude Code docs: How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- `--continue`/`--resume` reopen the same session ID and append to it. `--fork-session` or `/branch` copies history into a new ID. Checkpoints are separate from git, survive resume, cover only file changes, and cannot undo remote side effects such as databases or deployments — [same](https://code.claude.com/docs/en/how-claude-code-works)
- Auto-compaction summarizes near the context limit, and "detailed instructions from early in the conversation may be lost". Persistent rules go in CLAUDE.md. If one huge output refills context after every summary, auto-compaction stops after a few attempts and errors instead of looping — [same](https://code.claude.com/docs/en/how-claude-code-works)
- Local check on this machine (2026-11-09): one project directory held 92 session JSONL files, the largest 21 MB. The first record carries `sessionId`/`type`/`customTitle`. Full-log replay on resume therefore has to cope with very large logs — consistent with the docs above ([Claude Code docs](https://code.claude.com/docs/en/how-claude-code-works))

**OpenAI Codex CLI (third-party sources, 2026; not checked against official docs)**
- Sessions are saved as JSONL "rollout" files under `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`. `codex resume --last` / `codex resume` with a picker. Moving or compressing rollouts breaks resume — [Daniel Vaughan blog, Apr 2026](https://codex.danielvaughan.com/2026/04/11/codex-cli-session-lifecycle-resume-fork-rollouts); [InventiveHQ](https://inventivehq.com/knowledge-base/openai/how-to-resume-sessions)
- Two layers are reported: append-only JSONL for durability and a SQLite metadata index for fast lookup. Paginated thread history was added so resume scales (Jul 2026), and archiving arrived in v0.136 (Jun 2026). Version details conflict across these blogs — [Vaughan, Jul 2026](https://codex.danielvaughan.com/2026/07/23/codex-cli-paginated-thread-history-sqlite-session-resume-search-memories/); [Vaughan, Jun 2026](https://codex.danielvaughan.com/2026/06/08/codex-cli-session-lifecycle-archive-resume-fork-rollout-persistence-management/)

**LangGraph checkpointing (official docs)**
- Checkpoints are saved at super-step boundaries per `thread_id`, which is required for save and resume. If a node fails mid-super-step, the **pending writes** of nodes that succeeded in that step are stored, so resume does not re-run them. On replay, nodes after the checkpoint re-execute, including LLM calls and API requests. In "async" durability mode a crash can lose the latest checkpoint. JS and Python docs describe "sync" mode inconsistently — [LangGraph persistence (Python)](https://docs.langchain.com/oss/python/langgraph/persistence.md); [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

**Manus (Jul 18 2025)**
- The file system serves as unlimited external memory, with restorable compression (keep a path or URL instead of the content). A `todo.md` rewritten at the end of context keeps goals in recent attention over ~50-call loops. Failed actions and stack traces stay in context. Context is append-only so the KV cache survives — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

### Inferences
- The minimal resume design shared by Claude Code and Codex is an append-only JSONL log of every message, tool call and result, keyed by session ID. Resume replays the log, fork copies it to a new ID, and a separate index or metadata line makes listing fast. Because the log is append-only, it also keeps the prompt prefix stable for caching (Manus).
- For multi-session tasks, Anthropic's evidence is qualitative but specific. Machine-readable task state (JSON with pass/fail per item), a free-text progress file, git commits per unit of work and a bootstrap script cut the re-orientation steps a fresh session would otherwise spend. For TrackAI, a resumed session could load the progress file plus the last N log entries instead of replaying a multi-MB log.
- LangGraph's pending-writes idea maps onto tool calls. If tool results are logged as they complete, a crash during a parallel batch of reads need not re-run the finished calls. Side-effecting tools still need idempotency or an "already applied" check on replay.

### Gaps
- No source reports a controlled measurement (success rate, steps saved, tokens saved) for progress files, feature lists or session resume vs starting fresh.
- Official OpenAI Codex documentation on the rollout format was not checked. The Codex details come from third-party blogs that conflict on versions.
- OpenHands' event-stream persistence and session-restore design was not covered in this session.
